\section{What is an FPGA}
\label{sec:what_is_fpga}

\acp{fpga} are reconfigurable integrated circuits whose logic and
interconnect are defined by a configuration bitstream loaded at
runtime~\cite{Kuon2007}.
Unlike \acp{asic}, fixed at fabrication, or general-purpose processors,
which execute sequential software, \acp{fpga} deliver parallel hardware
execution while remaining reprogrammable.
Modern \ac{rfsoc}-class devices further integrate hardened processor
cores and \ac{rf} data converters on the same die, eliminating the
external converter interfaces required in multi-chip
architectures~\cite{Boppana2015}.


% ------------------------------------------------------------
\subsection{Internal Architecture}
\label{subsec:fpga_resources}

The programmable logic of a Zynq~UltraScale+ device is built from four
principal resource types: \acp{lut}, \acp{ff}, hardened DSP48E2 slices,
and \ac{bram}~\cite{AMD_UG574,AMD_UG579}.

\paragraph{Look-Up Tables:}
A \ac{lut6} implements any combinational Boolean function of up to six
inputs and is the fundamental logic primitive of the UltraScale+
fabric~\cite{AMD_UG574}.
Eight \ac{lut6} primitives are grouped with carry logic into a \ac{clb}.
A \ac{lut} may also be configured as distributed \ac{ram} or a
shift-register delay line, avoiding \ac{bram} consumption for shallow
buffering.

\paragraph{Programmable Interconnect:}
Logic resources are connected through switch boxes and routing channels
whose programmable pass transistors route signals between
\acp{clb}~\cite{AMD_UG574}.
In practice, routing delay through this fabric dominates critical-path
timing and is the primary constraint during timing closure.

\paragraph{Flip-Flops:}
Each \ac{lut6} is paired with one or more \ac{ff} registers that capture
logic values on the rising clock edge~\cite{AMD_UG574}.
Flip-flops break long combinational paths into shorter pipelined stages,
enabling the fabric to sustain higher clock frequencies.

\paragraph{DSP48E2 Slices:}
The DSP48E2 is a hardened arithmetic primitive providing a
27$\times$18-bit two's-complement multiplier cascaded with a 48-bit
accumulator~\cite{AMD_UG579}.
A dedicated cascade port allows adjacent slices to chain without
consuming general routing resources, making them well suited to
\ac{mac}-intensive operations such as \ac{fir} filtering.
The UltraScale+ family provides approximately 12{,}000 DSP48E2
slices capable of operating at approximately 900\,MHz~\cite{Boppana2015}.

\paragraph{Block RAM:}
\ac{bram} is a dedicated on-chip memory primitive available in 36\,Kbit
true dual-port units, supporting simultaneous read and write on
independent ports at the full fabric clock rate~\cite{AMD_UG574}.
The deterministic single-cycle read latency makes \ac{bram} suitable
for real-time streaming data paths.

\subsection{FPGA vs.\ ASIC: Why FPGA for Prototyping}
\label{subsec:fpga_vs_asic}

Three arguments motivate selecting an \ac{fpga} over an \ac{asic} or
software processor for the J.83B physical layer prototype: zero
\ac{nre} cost, parallel throughput exceeding the target symbol rate,
and the maturity of the UltraScale+ platform for \ac{rfsoc} development.

\paragraph{Reconfigurability and NRE Cost:}
Kuon and Rose measured the implementation gap between \ac{fpga} and
standard-cell \ac{asic} across 23 benchmark circuits at the 90\,nm
node: using reconfigurable fabric alone, the \ac{fpga} silicon area
is on average 35$\times$ larger, critical-path delay 3.4$\times$ slower,
and dynamic power 14$\times$ higher; exploiting hardened blocks such as
multiplier-accumulators and block memories narrows the area ratio
to 18$\times$~\cite{Kuon2007}.
These penalties are accepted in exchange for zero \ac{nre} cost and
instant design iteration: a bitstream reload replaces the multi-month
\ac{asic} re-spin cycle, making \acp{fpga} the standard substrate for
prototype and research-scale implementations~\cite{Kuon2007}.

\paragraph{Throughput Advantage Over Software Processors:}
Diouri et al.\ compared a 40th-order bandpass \ac{fir} filter on an
Altera Cyclone~III \ac{fpga} and a TMS320C6713 \ac{dsp} processor: the
\ac{fpga} achieved 3.4\,Gops/s at 122\,MHz drawing 95\,mW, versus
1.8\,Gops/s at 225\,MHz drawing 900\,mW for the
processor~\cite{Diouri2022}.
The throughput advantage arises from fully parallel datapath execution:
all \ac{mac} operations proceed simultaneously in hardware, whereas a
processor executes one per instruction cycle~\cite{Diouri2022}.
The 5.360537\,Msym/s J.83B symbol rate is well within the margin
available from a pipelined \ac{pl} fabric at 250\,MHz~\cite{ITU_J83}.

\paragraph{UltraScale+ as a Prototyping Substrate:}
The Zynq~UltraScale+ \ac{rfsoc} integrates reconfigurable logic, a
hardened \ac{arm} processor, and \ac{rf} data converters on a single
16\,nm FinFET die, delivering 60\% higher logic performance and
2.5$\times$ greater performance per watt relative to the preceding
28\,nm generation~\cite{Boppana2015}.
The specific platform used in this work and its subsystems are described
in Section~\ref{sec:rfsoc4x2}.

\section{FPGA Programming and Design Flow}
\label{sec:fpga_programming}

Hardware functionality is described in an \ac{hdl} and compiled into a
device-specific bitstream through synthesis, place-and-route, and
bitstream generation~\cite{AMD_UG892}.
This section describes that flow and its realization in the AMD Vivado
toolchain used in this work.

\paragraph{Synthesis:}
Vivado synthesis elaborates the \ac{hdl} source into a generic netlist
then maps it onto UltraScale+ primitives~\cite{AMD_UG892}.
Arithmetic and memory structures are inferred automatically:
multiply-accumulate operations map to DSP48E2 slices, and inferred
memories map to \ac{bram} or distributed \ac{ram} as appropriate.

\paragraph{Implementation:}
Implementation places each primitive at a physical site on the die
and routes the interconnect between them~\cite{AMD_UG892}.
The timing analyzer verifies that all paths meet setup and hold
constraints at the target clock frequency; if not, the \ac{rtl} or
directives are revised and the flow repeats.

\paragraph{Bitstream Generation and Hardware Handoff:}
Once timing closure is achieved, Vivado simultaneously generates the
binary \texttt{.bit} configuration file and exports the hardware
handoff (\texttt{.hwh}) from the block design~\cite{AMD_UG892}.
The \texttt{.hwh} records the \ac{ip} address map and interface
metadata used by the PYNQ overlay loader; together, the
\texttt{.bit} and \texttt{.hwh} constitute the complete \ac{pl}
overlay deliverable of this thesis~\cite{PYNQ_DOC,Kovacs2024}.


% ------------------------------------------------------------
\subsection{Vivado IP Integrator Block Design}
\label{subsec:ip_integrator}

The Vivado \ac{ip} Integrator is a graphical design canvas in which
\ac{ip} cores are instantiated as blocks and wired together through
their typed interface ports~\cite{AMD_UG994}.
The block design captures the full \ac{pl} hardware topology —
interconnect, clocking, and \ac{ps}--\ac{pl} port bindings — as a
single source artifact that drives both synthesis and
\texttt{.hwh} export.

\paragraph{IP Catalog:}
The \ac{ip} catalog is the searchable library from which cores are
instantiated onto the canvas~\cite{AMD_UG994}.
It includes Xilinx LogiCORE primitives, third-party cores, and
user-packaged custom \ac{rtl} modules added through a local
repository path; all cores expose typed bus interfaces so that
compliant connections can be made with a single wire on the canvas.

\paragraph{Address Editor:}
The address editor assigns each \ac{axi}4-Lite slave a unique base
address within the \ac{ps} memory map~\cite{AMD_UG1085}.
These assignments are exported to the \texttt{.hwh} file at
implementation and consumed by the PYNQ overlay parser to construct
the Python \ac{ip} dictionary described in
Section~\ref{subsec:pynq_overlay}~\cite{PYNQ_DOC}.


% ------------------------------------------------------------
\subsection{IP Packaging: Custom RTL Modules}
\label{subsec:ip_packaging}

Before a custom \ac{rtl} module can be instantiated in the block
design, it must be packaged as a Vivado \ac{ip} core using the
Vivado \ac{ip} Packager, which wraps the source hierarchy in a
standardized IP-XACT descriptor~\cite{AMD_UG994}.

\paragraph{AXI Port Inference:}
The packager infers \ac{axi} interface types from port naming
conventions: \texttt{s\_axis\_*} / \texttt{m\_axis\_*} ports are
grouped into typed \ac{axi}4-Stream interface objects, and
\texttt{s\_axi\_*} ports are inferred as \ac{axi}4-Lite register
file interfaces~\cite{AMD_UG994}.
This allows the block design canvas to connect compliant interfaces
with a single wire rather than individual port-to-port connections.

\paragraph{component.xml:}
The packaging step produces a \texttt{component.xml} file defining
the core's port groupings, bus interface protocols, and
user-visible parameters~\cite{AMD_UG994}.
The packaged core is stored in the Vivado \ac{ip} repository and is
available for instantiation in any block design referencing that
path, supporting a modular flow in which each J.83B processing
stage is developed and packaged independently before
integration~\cite{Kovacs2024}.

\subsection{Processing System: ARM Cortex-A53}
\label{subsec:ps_arm}

The \ac{ps} of the ZU48DR contains a quad-core ARM Cortex-A53
\ac{apu} running at up to 1.2\,GHz with a 64-bit \ac{ddr}4

\subsection{RF Data Converter: DAC/ADC Architecture}
\label{subsec:rfdc_background}

The ZU48DR integrates four \ac{rf}-\ac{adc} tiles and four
\ac{rf}-\ac{dac} tiles, each containing two converter channels
clocked by a shared sample clock~\cite{AMD_PG269}.

\paragraph{RF-ADC:}
Of the eight \ac{rf}-\ac{adc} channels, four are routed to
board-accessible \ac{sma} connectors on the RFSoC~4x2
board~\cite{Kovacs2024}.
Each accessible channel is a 14-bit converter capable of sampling
at up to 5\,\ac{gsps}, with an integrated \ac{ddc} block that
downconverts the \ac{rf} sample stream to a complex \ac{iq} output
presented to the \ac{pl} as a 32-bit \ac{axi}4-Stream (16-bit I,
16-bit Q) at the fabric clock rate~\cite{AMD_PG269}.

\paragraph{RF-DAC:}
Of the eight \ac{rf}-\ac{dac} channels, two are routed to
board-accessible \ac{sma} connectors~\cite{Kovacs2024}.
Each accessible channel is a 14-bit converter operating at up to
9.85\,\ac{gsps}, with an integrated \ac{duc} that accepts a
32-bit \ac{axi}4-Stream from the \ac{pl} and upconverts to the
\ac{rf} sample rate~\cite{AMD_PG269}.

\paragraph{Latency Advantage:}
Monolithic integration of the converters eliminates the external
serial interface required in discrete converter architectures.
Javaid et al.\ measured loopback latencies of 108\,ns (real) and
246\,ns (complex \ac{iq}) on a first-generation \ac{rfsoc} at
250\,MHz stream clock, compared to approximately 1.66\,$\mu$s for
an equivalent JESD204-based solution — an 80--90\,\% reduction
attributable to the elimination of JESD204 lane alignment
buffering~\cite{Javaid2022}.

\subsection{PS-PL Integration Model}
\label{subsec:ps_pl_integration}

The \ac{ps} and \ac{pl} subsystems communicate through a set of
\ac{axi} interconnect ports that form the data and control paths
between the \ac{arm} processor and the reconfigurable
fabric~\cite{Boppana2015,AMD_UG1085}.

\paragraph{High-Performance Ports:}
The \ac{hp} \ac{axi} slave ports connect the \ac{pl} to the \ac{ps}
memory subsystem at high bandwidth, supporting up to 85\,Gbps per
port for combined read-plus-write traffic~\cite{Boppana2015}.
These ports carry bulk data transfers between the \ac{pl} processing
pipeline and \ac{ddr}4 system memory~\cite{AMD_UG1085}.

\paragraph{AXI DMA:}
\label{subsec:axidma_background}% retained: cross-referenced by frozen §2.6
The \ac{axi} \ac{dma} is a Xilinx LogiCORE \ac{ip} block that
bridges the \ac{axi}4 Full \ac{hp} ports of the \ac{ps} memory
system and the \ac{axi}4-Stream interfaces of the \ac{pl}
fabric~\cite{AMD_PG021}.
It provides two independent channels: \ac{mm2s} reads a contiguous
block from system memory and presents it as an \ac{axi}4-Stream to
the \ac{pl}; \ac{s2mm} accepts an \ac{axi}4-Stream from the \ac{pl}
and writes it into system memory~\cite{AMD_PG021}.
In simple mode a single transfer is initiated by writing the address
and byte count to the \ac{dma} control registers; in
scatter-gather mode a linked list of buffer descriptors drives a
sequence of transfers autonomously, reducing interrupt overhead for
multi-packet data movement~\cite{AMD_PG021}.

\paragraph{General-Purpose Ports:}
The general-purpose \ac{axi} master ports provide the \ac{ps} with
memory-mapped register access to \ac{ip} cores in the \ac{pl} for
control and status register operations~\cite{AMD_UG1085}.

\paragraph{Interrupt Routing:}
\ac{pl}-generated interrupt signals are routed to the \ac{ps}
\ac{apu} interrupt controller, enabling the PYNQ \ac{dma} driver
to block on transfer completion without polling~\cite{Kovacs2024}.

\section{AXI Interconnect Ecosystem}
\label{sec:axi}

The \ac{amba} \ac{axi}4 protocol family defines the standard on-chip
interconnect used throughout the Zynq~UltraScale+ device~\cite{ARM_IHI0022}.
This work uses two of its sub-protocols: \ac{axi}4-Stream for
high-throughput unidirectional data pipelines, and \ac{axi}4-Lite for
low-complexity register access.

% ------------------------------------------------------------
\subsection{AXI4-Stream: Data Path Protocol}
\label{subsec:axis}

\ac{axi}4-Stream is a unidirectional point-to-point streaming protocol
that carries a data payload between a single source and sink without
address signaling, making it well suited to deeply pipelined \ac{dsp}
datapaths~\cite{ARM_IHI0022}.
The interface is defined by four signals: \texttt{TDATA} carries the
payload; \texttt{TVALID} (source) indicates valid data;
\texttt{TREADY} (sink) indicates readiness to accept; and
\texttt{TLAST} marks the final beat of a packet~\cite{ARM_IHI0022}.
A transfer occurs on any rising clock edge on which both
\texttt{TVALID} and \texttt{TREADY} are asserted; de-asserting
\texttt{TREADY} applies backpressure that stalls the source until
the transfer can be accepted, allowing the pipeline to self-regulate
without data loss~\cite{ARM_IHI0022}.


% ------------------------------------------------------------
\subsection{AXI4-Lite: Control/Register Interface}
\label{subsec:axilite}

\ac{axi}4-Lite is a simplified subset of \ac{axi}4 Full designed for
low-throughput register read and write transactions~\cite{ARM_IHI0022}.
It retains the five-channel handshake structure of \ac{axi}4 Full but
restricts transfers to a single beat at a fixed 32-bit data width,
eliminating burst and unaligned-transfer complexity and producing an
interface compact enough to include in every \ac{ip} core without
significant resource overhead~\cite{ARM_IHI0022}.
In the Zynq~UltraScale+ \ac{ps}--\ac{pl} model, the \ac{ps} acts as
the \ac{axi}4-Lite master and each \ac{pl} \ac{ip} core acts as a
slave exposing a word-addressed register file; the Vivado address
editor assigns each slave a unique base address so that the
Cortex-A53 can access any register through ordinary load and store
instructions~\cite{AMD_UG1085}.

\section{RF Clocking Architecture}
\label{sec:rf_clocking_background}

Accurate, low-noise clocking is a prerequisite for high-order
\ac{qam} modulation.
In a \ac{qam256} system, phase noise on the sample clock or
distribution network rotates symbol clusters in the \ac{iq} plane,
degrading \ac{evm} beyond the level correctable by the \ac{fec}
stack~\cite{proakis_dsp}.
The \ac{rfsoc}~4x2 board addresses this through a three-device
clocking hierarchy~\cite{RealDigital_A6}: a Skyworks Si5395 jitter
attenuator generates the primary \ac{ps} and \ac{pl} fabric clocks;
a Texas Instruments LMK04828 jitter cleaner drives two Texas
Instruments LMX2594 \ac{rf} frequency synthesizers; each LMX2594
delivers the high-speed sample clock to the \ac{rfdc} \ac{dac} or
\ac{adc} tiles~\cite{RealDigital_A6}.


% ------------------------------------------------------------
\subsection{Clock Requirements for Multi-GHz DAC/ADC}
\label{subsec:clock_requirements}

The clocking hierarchy spans two independent frequency domains:
the \ac{rfdc} sample clock domain and the \ac{pl} fabric clock domain.

\paragraph{RFDC Sample Clock Domain:}
The \ac{rfdc} \ac{dac} tile sample rate is set by the J.83B symbol
rate and the oversampling factor of the \ac{srrc} pulse shaping filter:

\begin{equation}
  f_\text{sample} = f_\text{sym} \times N_\text{sps}
                  = 5.360537\,\text{Msym/s} \times 6
                  = 32.163\,\text{MSamp/s}
  \label{eq:sample_rate}
\end{equation}

\noindent where $N_\text{sps} = 6$ is the number of samples per symbol
and $f_\text{sym} = 5.360537$\,Msym/s is the J.83B Annex~B symbol
rate~\cite{ITU_J83}.
Meeting the \ac{evm} requirement of the J.83B \ac{qam256} channel
demands a sample clock source with sufficiently low phase noise that
jitter remains a small fraction of the minimum symbol
spacing~\cite{proakis_dsp}; the LMK04828 described in
Section~\ref{subsec:lmk04828_background} provides this reference.

\paragraph{PL Fabric Clock Domain:}
The \ac{pl} fabric operates from \texttt{pl\_clk} at 250\,MHz,
independent of the \ac{rfdc} sample clock; the two domains are
separated by \ac{axi}4-Stream \ac{cdc} \ac{fifo} stages within the
\ac{rfdc} \ac{ip} block~\cite{AMD_PG269}.
All \ac{rtl} modules in the J.83B processing pipeline are constrained
to the 250\,MHz \ac{pl} domain, while \ac{rfdc} sample-rate timing is
governed solely by the external clock from the LMK04828~\cite{AMD_UG1085}.


% ------------------------------------------------------------
\subsection{LMK04828: Jitter Cleaner and Clock Distributor}
\label{subsec:lmk04828_background}

The LMK04828 is a dual-loop clock conditioner manufactured by Texas
Instruments that occupies the second stage of the clocking hierarchy,
receiving a 10\,MHz reference from the Si5395 and a 160\,MHz
\ac{vcxo} input~\cite{TI_LMK04828,RealDigital_A6}.

\paragraph{Role in This Work:}
The LMK04828 provides the cleaned low-jitter reference that the
LMX2594 synthesizers require to generate stable sample clocks for
the \ac{rfdc} tiles, and supplies supplementary \ac{pl} fabric
reference clocks to the ZU48DR~\cite{RealDigital_A6}.
Lock status for each internal loop is indicated by the \texttt{PLL1}
and \texttt{PLL2} \acp{led} on the board~\cite{RealDigital_A6}.


% ------------------------------------------------------------
\subsection{LMX2594: RF Frequency Synthesizers}
\label{subsec:lmx2594_background}

The \ac{rfsoc}~4x2 board populates two LMX2594 wideband
fractional-$N$ \ac{pll} synthesizers~\cite{TI_LMX2594}: one
(\texttt{PLL1}) supplies the sample clock reference to the
\ac{rf}-\ac{adc} tiles; a second (\texttt{PLL2}) supplies the
\ac{rf}-\ac{dac} tiles~\cite{RealDigital_A6}.

\paragraph{Role in This Work:}
The two LMX2594 devices are the final stage of the clocking chain
and the direct source of the high-frequency sample clock references
consumed by the \ac{rfdc} \ac{dac} and \ac{adc}
tiles~\cite{RealDigital_A6}.
Their phase noise therefore sets the achievable \ac{evm} floor for
the J.83B \ac{qam256} signal~\cite{proakis_dsp}.
The J.83B \ac{rf} carrier frequency is not produced by the LMX2594;
it is synthesized digitally by the \ac{nco} within the \ac{rfdc}
\ac{duc}~\cite{AMD_PG269}.


% ------------------------------------------------------------
\subsection{xrfclk Software API}
\label{subsec:xrfclk_background}

The \texttt{xrfclk} library is an open-source Python package
distributed by Xilinx that abstracts the low-level \ac{spi}
register programming of the LMK04828 and LMX2594~\cite{xrfclk}.
A single function call from the PYNQ environment selects and writes
the pre-computed register sequences for a target sample rate,
configuring both clock devices without requiring device-specific
register maps in the host application~\cite{xrfclk}.

\paragraph{Integration with PYNQ:}
The \texttt{xrfclk} library is pre-installed in the PYNQ Linux image
provided with the \ac{rfsoc}~4x2 board and is invoked from the same
Jupyter notebook used to load the \ac{pl} overlay~\cite{RealDigital_A6,PYNQ_DOC}.
The specific function calls and target frequency arguments used in
this implementation are deferred to Chapter~4.

\section{PYNQ Framework}
\label{sec:pynq_background}

The PYNQ framework is an open-source software environment developed
by Xilinx that provides a Python-based interface to the programmable
logic of Zynq~UltraScale+ devices, eliminating the need for embedded
C or bare-metal software to interact with custom \ac{pl}
hardware~\cite{PYNQ_DOC}.
It enables a two-layer design methodology in which hardware-intensive
signal processing executes in the \ac{pl} at full hardware speed while
orchestration, configuration, and data movement are managed from a
Jupyter notebook running on the Cortex-A53 Linux
environment~\cite{Kovacs2024,PYNQ_DOC}.
The \ac{rfsoc}~4x2 board ships with PYNQ pre-installed, including the
\texttt{xrfclk} clock library and \ac{rfdc} Python driver, requiring
no separate toolchain to begin running custom \ac{pl}
designs~\cite{RealDigital_A6,PYNQ_DOC}.


% ------------------------------------------------------------
\subsection{Overlay Concept: .bit + .hwh + Python Driver}
\label{subsec:pynq_overlay}

An overlay is a complete \ac{pl} hardware configuration packaged as
three co-dependent artifacts: a bitstream (\texttt{.bit}), a hardware
handoff file (\texttt{.hwh}), and a Python driver class~\cite{PYNQ_DOC}.

\paragraph{Bitstream:}
The bitstream (\texttt{.bit}) programs the UltraScale+ \ac{pl} fabric
with the target hardware design, produced by the Vivado implementation
flow described in Section~\ref{subsec:vivado_flow}~\cite{PYNQ_DOC}.

\paragraph{Hardware Handoff File:}
The \texttt{.hwh} is an \ac{xml} description of the block design
exported by Vivado at implementation time~\cite{PYNQ_DOC}.
It encodes the address map of every \ac{pl} \ac{ip} core, the width
and connectivity of each \ac{axi}4-Lite register file, and the
interrupt routing from \ac{pl} to \ac{ps}~\cite{PYNQ_DOC}.
When an overlay is loaded in Python, PYNQ parses the \texttt{.hwh}
to auto-generate a register-level driver dictionary for every \ac{ip}
core, making the \ac{pl} hardware immediately accessible without
handwritten register definitions~\cite{PYNQ_DOC}.

\paragraph{Python Driver Class:}
The driver calls \texttt{Overlay()} with the \texttt{.bit} and
\texttt{.hwh} paths, which programs the \ac{pl} and populates an
\ac{ip} dictionary keyed by core name~\cite{PYNQ_DOC}.
The PYNQ library provides pre-built driver subclasses for common
Xilinx \ac{ip} cores, including the \ac{axi} \ac{dma}~\cite{PYNQ_DOC}.


% ------------------------------------------------------------
\subsection{PYNQ DMA and IP Drivers}
\label{subsec:pynq_drivers}

\paragraph{DMA Driver:}
The \texttt{pynq.lib.dma.DMA} class wraps the \ac{axi} \ac{dma}
register interface into a Python object with \ac{mm2s} and \ac{s2mm}
channel attributes~\cite{PYNQ_DOC}.
Each channel exposes a \texttt{transfer()} method that accepts a
\ac{dma}-capable buffer, writes the address and byte count to the
\ac{dma} control registers, and optionally blocks until the \ac{dma}
raises its completion interrupt~\cite{PYNQ_DOC}.

\paragraph{IP Register Access:}
For custom \ac{rtl} modules exposing an \ac{axi}4-Lite register file,
PYNQ auto-generates a register accessor from the \texttt{.hwh} address
map at overlay load time~\cite{PYNQ_DOC}.
Each \ac{ip} core appears as an entry in the overlay's
\texttt{ip\_dict}, keyed by the instance name assigned in the Vivado
block design, allowing runtime configuration of any \ac{pl} module
without additional driver development~\cite{PYNQ_DOC}.

\section{MATLAB-to-RTL Workflow}
\label{sec:matlab_rtl}

The J.83B signal processing chain was first developed as a MATLAB
floating-point reference model, with MathWorks HDL Coder identified
by ANSpect as the primary path for generating synthesizable \ac{rtl}
directly from that model~\cite{HDLCoder}.
This section describes the intended HDL Coder workflow, the
limitations encountered during its evaluation, and the engineering
decision that resulted.


% ------------------------------------------------------------
\subsection{HDL Coder: Intended Path}
\label{subsec:hdlcoder_intended}

MathWorks HDL Coder is a toolbox that generates synthesizable
\ac{vhdl} or Verilog \ac{rtl} from MATLAB functions and Simulink
models, intended to be directly importable into Vivado without
manual translation of the algorithm into a fixed-point hardware
description~\cite{HDLCoder}.

\paragraph{Specified Workflow:}
The ANSpect \ac{fpga} specification identified HDL Coder as the
\ac{rtl} generation method for five of the eight J.83B processing
blocks: the \ac{srrc} pulse shaping filter, the randomizer, the
trellis encoder, the \ac{qam256} symbol mapper, and the \ac{rs}
encoder~\cite{HDLCoder}.
The intended workflow for each block was to develop and verify a
MATLAB or Simulink model, apply HDL Coder to generate a fixed-point
SystemVerilog or \ac{vhdl} netlist, package the output as a Vivado
\ac{ip} core, and integrate it into the top-level block
design~\cite{HDLCoder}.
The remaining three blocks — the convolutional interleaver, the frame
sync encoder, and the transport framing stage — were identified as
manual \ac{rtl} candidates due to their state-machine-intensive
control structures.


% ------------------------------------------------------------
\subsection{HDL Coder Limitations Encountered}
\label{subsec:hdlcoder_limitations}

Evaluation of HDL Coder against the five specified blocks revealed
three categories of limitation that prevented the generated \ac{rtl}
from meeting the integration requirements of the Vivado block design
flow.

\paragraph{AXI4-Stream Interface Generation:}
HDL Coder does not natively generate \ac{axi}4-Stream interfaces;
it generates a data-valid handshake without \texttt{TREADY}
backpressure support~\cite{HDLCoder}.
Adapting the generated \ac{rtl} to a fully compliant \ac{axi}4-Stream
interface requires a manually written wrapper, negating the
code-generation advantage for any block that must participate in a
streaming pipeline with variable-rate stages.

\paragraph{AXI4-Lite Register File:}
HDL Coder does not generate \ac{axi}4-Lite register files for runtime
configuration of processing parameters~\cite{HDLCoder}.
Every block requiring runtime parameter access — including the
interleaver depth selector, the randomizer initialization trigger,
and the frame sync detector threshold — requires a hand-written
\ac{axi}4-Lite register file, making the HDL Coder output a partial
solution that still requires substantial manual \ac{rtl} work.

\paragraph{Core Datapath Output Only:}
HDL Coder generates \ac{rtl} for the core arithmetic datapath of a
block but does not generate the surrounding infrastructure required
for integration into a Vivado \ac{ip} core~\cite{HDLCoder}.
The generated output omits the finite-state machine, pipeline
enable and stall control logic, \ac{axi}4-Stream handshake wrapper,
and \ac{axi}4-Lite register file — each of which must be written
manually before the block constitutes an integration-ready
\ac{ip} core~\cite{HDLCoder}.


% ------------------------------------------------------------
\subsection{Decision: Manual RTL Coding}
\label{subsec:manual_rtl_decision}

The three limitation categories established that HDL Coder could not
produce integration-ready \ac{rtl} for the J.83B processing blocks
without manual effort comparable to writing the \ac{rtl} from scratch;
all \ac{pl} modules are therefore implemented as hand-coded
SystemVerilog.

\paragraph{RTL Language and Interface Standard:}
All J.83B processing blocks and their supporting infrastructure
except Vivado \ac{ip} are implemented in SystemVerilog, with native
\ac{axi}4-Stream data interfaces and \ac{axi}4-Lite control interfaces
coded directly to the \ac{amba} specification described in
Section~\ref{sec:axi}.
Each module is self-contained, fully pipelined, and packaged as a
Vivado \ac{ip} core per the flow described in
Section~\ref{subsec:ip_packaging}.

\paragraph{Retained Role of MATLAB:}
The MATLAB reference model is retained as a verification tool rather
than a code generation source.
The reference scripts generate bit-exact test vectors for each
processing stage; these vectors are applied to the SystemVerilog
modules in simulation and the outputs are compared against the MATLAB
reference to confirm algorithmic correctness before the design is
taken to hardware.
